00

Why a new render chain

The harness leaves; the prompt does its job.

The current CLAUDE.md ships ~3,000 tokens, a meaningful fraction of which assumes a Claude Code harness — auto-memory suppression, env-var hygiene, context-window management, tool injection by system-reminder. Moving shells onto local 8B models removes that harness. What it carried implicitly, the rendered prompt has to carry explicitly. At the same time, an 8B cannot absorb the same volume a frontier model can: the prompt has to shed weight while gaining specificity.

What this spec proposes

  • A typed section catalog, rendered from the DB at every boot, ordered identity → scope → tools → constraints → output.
  • Dialect-aware tool rendering — anthropic / openai / parsed — keyed off chat_sessions.model_id → models.tool_dialect.
  • A common/specific tooling split: common tools in the render chain, specific tools embedded in skills.
  • Soft caps by instruction, not by BEFORE INSERT triggers. Trust the shell to aim; accept occasional overrun rather than pay the retry tax.
  • A parallel summarizer (small local model) running between turns to compress chat into a context block, while the active shell continues unblocked.
Target ~6–7k tokens per rendered prompt. Proof-of-concept, not a budget yet. Universal layer concatenated with per-shell layer; both come from the renderer, both leave on every boot.

What's not changing

The substrate API stays the source of truth for memory writes. The shell never reaches the DB directly. The seed / lns count caps (10 / 20) stay enforced — those are about curation, not tokens. The Laws stay universal and immutable.

01

Render pipeline

From template + DB to rendered prompt, in eight stages.

The renderer is the existing shell_core/scripts/run.py family, extended. It fires on shell boot at minimum, and optionally on inflection events (current_state mutation, model switch). Output lands at the shell's working path as CLAUDE.md (name retained for compatibility; the file is no longer Claude-specific).

Resolve identity
shell_id · chat_session_id · user_id from launcher env
ii
Capture wall-clock
datetime.now() — boot context section needs it; the model has no clock
iii
Fetch shell row
SELECT * FROM shells WHERE shell_id = ?
iv
Resolve model + dialect
chat_sessions → models · pick tool_dialect, context_window, locality
v
Hydrate related rows
identity_entries · skills · tools · projects · archive · (decisions: optional)
vi

vii
Assemble
Universal template → per-shell template → concatenate
viii

CLAUDE.md at the shell's working path; shell boots reading it

Render frequency

Per-session at minimum. Per-turn re-render is on the table for current_state propagation but introduces cost — the system prompt is paid every turn already, but recomputing it adds latency. Open question #1.

02

Section catalog

Identity frames first; constraints stick last.

Following the optimization guide: top sets attention, bottom sets adherence. A finding for the current render — the Laws move toward the bottom. They are critical constraints, and recency keeps them honored. The top names who and why; the bottom names how and what-must-not.

One section (⌂) is computed at render time, not pulled from the DB: Boot context. It carries the wall-clock date and time the renderer fired, plus the session metadata (shell_id, session_id, archive_id). Local models have no clock; the operations that need one — narrative entries with [HH:MM], identity-entry entry_date, decision dates — fail or hallucinate without this section.

04

Soft caps

From triggers to instruction.

The current schema enforces body lengths with BEFORE INSERT triggers that abort over-cap writes. Net effect on a shell: the write fails, the shell retries (sometimes several times, sometimes hallucinating shorter content that loses signal), and turns get spent on plumbing instead of work. Claude Code itself doesn't hard-cap memory entries — it suggests, the model aims.

The proposal: drop the body-length triggers, keep the count caps. Replace the enforcement with rendered instruction the shell can aim at.

04.1Soft targets, by entry

FieldCurrent hardcapProposed soft targetRendered as
seed.body800~500 chars"distilled moment, not a log — aim ~500"
lns.body400~500 chars"a working principle — aim ~500"
current_state280~500 chars"rolling now/next — aim ~500, replace in place"
dr_*.description_short100~80 chars"one-line description — aim ~80"
dr_log.change_summary50~50 chars"terse changelog entry — aim ~50"

04.2Triggers to remove

  • DROPtrg_sie_body_cap_seed
  • DROPtrg_sie_body_cap_lns
  • DROPtrg_current_state_cap_insert
  • DROPtrg_current_state_cap_update
  • DROPCHECK (LENGTH(description_short) <= 100) on dr_* tables
  • DROPCHECK (LENGTH(change_summary) <= 50) on dr_log

04.3Triggers to keep

  • KEEPtrg_sie_cap_seed — count = 10. Curation, not length.
  • KEEPtrg_sie_cap_lns — count = 20. Curation, not length.
  • KEEPtrg_dr_sync_runs_rolling — operational hygiene.
Trade-off accepted Occasional overrun is cheaper than the retry tax. A shell that writes a 700-char seed when the target was 500 is not broken — it found something dense and worth holding. A shell that hits an ABORT three turns in a row is.
05

Tool dialects

Three ways to teach a tool — the seam already exists.

models.tool_dialect is already a CHECK-constrained column: anthropic, openai, parsed. This is where dialect-awareness lives. The renderer reads it via chat_sessions → models and branches the tool section accordingly.

05.1Per-dialect rendering

anthropic / openai

The provider applies the schema out-of-band. The prompt only needs a roster: tool name + one-line purpose. No worked example required.

tools available:
  identity_write     — POST seed/L&S entries to substrate
  decision_record    — POST a Major decision
  flag_open          — POST a new flag
  ...

parsed

The provider does not apply a schema. The local 8B has to form the call itself, in text, which the harness then parses. The prompt has to teach it. For each tool:

  • Name + one-line purpose
  • Compact param list with types and required-ness
  • One worked invocation example
  • One refusal/fallback example for when params can't be formed
tool: identity_write
purpose: append a seed or L&S entry
params:
  kind     str  required  one of: seed | lns
  body     str  required  ~500 chars
  source   str  optional  short tag

invoke:
  <tool:identity_write>
    kind: lns
    body: prefer editing existing files over creating new ones
  </tool>

if you cannot form a valid call, say so:
  i don't have what i need to record this — i need {missing}

05.2Where the parsed example lives

Three options for storing the hand-authored example for parsed dialect:

OptionProCon
Bake into tools.specNo schema changeCouples spec to dialect; muddies the JSON schema
Add tools.parsed_example TEXTClean separation; nullable; hand-authored once per toolSchema delta

Recommendation: option 2. A new nullable tools.parsed_example TEXT column, populated for tools that need parsed support. Frontier shells never read it; local shells render it inline.

06

Tooling boundary

Common in the render chain. Specific in the skills.

Not every tool needs to live in the prompt every turn. A two-layer split — universal vocabulary always rendered, specialized vocabulary rendered only when its skill is invoked — keeps the common section tight and lets skills carry their own surface area.

06.1Common tools (rendered every turn)

The vocabulary every shell needs to maintain itself and its memory. Roughly six to ten endpoints; budget ~400–800 chars depending on dialect.

ToolEndpointPurpose

identity_retirePATCH …/identity-entries/{eid}Curate out (preserves row)

06.2Specific tools (embedded in skills)

Every other capability lives inside the skill that needs it. The skill's name + description render in the SKILLS section always; the full content — including any tool grammar specific to that skill — is fetched on demand when the shell invokes the skill.

  • database-migrations — author migration files, run make db-migrate
  • catalogue_sync — invoke the populator, surface dr_* state
  • skill_management — skill CRUD endpoints
  • git-workflow — identity-prefix env vars, stacked-PR rules
  • db_backup — snapshot before structural change
  • … and so on
Why the split Common renders always — paid once per turn, ~600 chars amortized. Specific renders only when its skill is fetched — paid only when used. A shell with 20 skills doesn't pay for 20 tool grammars in every system prompt; it pays for the one it just opened.

The shape of what each skill carries — workflow, not just tools — is the subject of section 07.

07

Skills as workflows

Tool-narrowing by design — workflow-prescriptive, not tool-bundled.

A flat tool surface — twenty tools visible at once — is a 1-of-20 selection problem. 8B reliability there lands somewhere around 50–70% even with good descriptions. Surfacing tools through skills collapses the decision: by the time a skill is invoked, the universe of relevant tools is three or four, and the surrounding procedure is named. We trade "choose any tool" for "execute this procedure with these tools." That's a problem 8B handles well.

This isn't unique to Design/OS — Cursor, Aider, and Claude's own skill system are built on the same insight. What this section commits to is the variant we want: skills as prescribed workflows, with their tools, sequences, and decision points authored together in skills.content.

07.1The reliability shape

Architecture8B reliability · single-taskWhere planning happens
Flat tool surface · 20+ tools visible always40–55%Model, at runtime, every turn
Skill = tool bundle · interpretation A65–80%Model, at runtime, narrowed scope
Skill = prescribed workflow · interpretation B80–90%Author, at authoring time

The architecture buys ~20–30 percentage points. That's the difference between "demo works, production doesn't" and "production works, occasionally needs a retry."

07.2Two interpretations, one chosen

ApproachWhat the skill carriesWhat the model doesCeiling at 8B
A · Tool bundle Tool definitions, surfaced when invoked Picks tools, sequences them, decides branches at runtime ~80%
B · Prescribed workflow Tools + canonical sequence + decision points + recovery Executes the procedure; branches only at authored choice points ~90%

We commit to B. Tools are building blocks; skills are the assemblies. Planning is moved out of the inference loop and into the authoring step, where it can be done once, by the operator, with intent.

07.3What goes in skills.content

The skills.content field becomes a load-bearing authoring surface. A skill renders fully only when invoked, but when it does, it carries everything the shell needs to do the work:

  1. When to invoke — trigger conditions in concrete language
  2. Tools surfaced — definitions, with parsed_example on local dialects
  3. Canonical sequence — the order operations happen in by default
  4. Decision points — branches with their conditions stated
  5. Recovery — what to do when a step fails, and when to stop

Example shape — the database-migrations skill, written for a local 8B shell:

purpose: evolve the substrate's SQLite schema

invoke when: adding or altering a table, column, trigger,
             or running a data backfill

tools available in this skill:
  snapshot_db        POST /db/snapshot
  create_migration   filesystem write at shell_core/migrations/NNN_*.sql
  run_migration      subprocess: make db-migrate
  rollback           POST /db/restore { snapshot_id }

workflow:
  1. snapshot_db                       → backup before any change
  2. create_migration                  → author the .sql file
  3. update schema.sql in same change  → keeps fresh-clone path in sync
  4. run_migration                     → apply against live DB
  5. verify schema; if fails → rollback to snapshot_id from step 1

never:
  - run_migration without snapshot_db first
  - hand-edit schema.sql without a paired migration file
  - leave step 3 out — the two paths must agree

stop:
  - after rollback (escalate to operator)
  - after verify success (announce; do not chain further skills)

The shell sees this on invocation, not on every boot. The SKILLS section in the boot prompt (section F) only lists name + trigger description.

07.4Two trigger types · explicit and context

A skill should be invocable two ways: deterministically, when the operator names the skill; and probabilistically, when the model recognizes the work in front of it as the kind a skill exists for. Both have a place. They have different demands.

TypeWho fires itHowReliability
Explicit Operator (or the shell, when its own intent is clear) A flag-like token in the message: --db-backup ~100% — string match, not inference
Context Shell, recognizing the situation Keyword match against the skill's tag list, weighted with a short description ~85–90% on Qwen3-8B with tight keywords

Explicit triggers

A token form: --{skill-name}. Lower-kebab-case, matches the skills.name field. The harness intercepts before the model sees the message: if the token appears, the skill content is loaded into the next turn as context, no inference required. Examples:

--db-backup
--catalogue-sync
--flag-triage
--identity-curation

This is the escape hatch for when the operator knows what they want and doesn't want to negotiate with the model's interpretation. It's also the way one skill calls another deterministically — by emitting --{next-skill} as part of its own output, the model hands off without re-deciding.

Context triggers

Each skill carries a small keyword set plus a short description. The keywords are the matching surface; the description is the disambiguator the model reads after a keyword fires. Both render in Section F every turn. Both are tight: keywords are nouns or short verb phrases, descriptions are one sentence.

db-backup            # --db-backup
  keywords: backup, snapshot, before migration, restore point, dump db
  use when: about to make a structural change to the DB and want to be
            able to roll back

catalogue-sync       # --catalogue-sync
  keywords: dr_ drift, sync runs, populator, catalogue stale, dr_sync_runs
  use when: dr_* tables look stale or the cron sync is silent

flag-triage          # --flag-triage
  keywords: open flags, prioritize, schedule, what's blocking, sprint
  use when: prioritizing or sequencing open flags

identity-curation    # --identity-curation
  keywords: seed, L&S, retire, rewrite my lessons, cap reached
  use when: managing your own identity entries — retiring or replacing

The model scans Section F looking for a keyword that matches the operator's request, reads the use when, decides. Keywords compress the matching step; the use when handles the close calls.

Authoring rules for both

FieldRule
explicit triggerAlways --{skill.name}. Lower-kebab. One per skill. Auto-generated, not authored.
keywords3–6 entries. Nouns or short verb phrases. Distinctive — avoid generic stems like "update" or "manage" that appear in five other skills.
use whenOne sentence, ≤120 chars. Names the trigger condition concretely. Not "manages X"; rather "use when changing X or running Y".
nameLower-kebab. Semantically distinct from siblings. db-backup not db-ops.

Disambiguation when keywords collide

If two skills share a keyword — e.g., "flag" appears in both flag-triage and flag-resolution — the use when sentence does the discrimination. The harness can also pre-score by counting unique keyword matches: a query containing two of flag-triage's keywords and one of flag-resolution's gets the former, without reaching the model at all. This pre-scoring is optional and worth measuring before building.

Before / after

Don't · capability-focusedDo · two-trigger, keyword-tagged

keywords: backup, snapshot, before migration, restore

07.5Where failures still happen

Being honest about the ceiling, with the new architecture:

  • Context-trigger mis-selection · ~10–15%. Distinct keywords and tight use whens compress this; explicit triggers --{name} bypass it entirely when the operator knows what they want. The mitigation is teaching operators that explicit triggers exist.
  • Cross-skill workflows · don't try. "Run a migration, then update the docs, then commit" spanning three skills exceeds 8B's reliable planning depth. Fold the work into one skill, or have skill A emit --{skill-b} as its final action to hand off deterministically.
  • Mid-skill error recovery · weak. When step 3 of a workflow fails, 8B will often retry step 3 with the same broken inputs rather than backing up to step 2. The harness has to detect failure, surface it, and either auto-retry from a known state or hand off.
  • Keyword collisions · author-time problem. Two skills both matching "update" is a bug, not a runtime concern — fix the keyword set.

07.6Mitigations

  • A meta-skill no_skill_needed (or an explicit "respond directly" rule in section F) so the model has a clean out when nothing fits
  • Tight, semantically distinct skill names — db-backup and db-restore beat db-ops
  • Single skill = single task scope. Resist composability. Accept the duplication.
  • Explicit triggers as the deterministic handoff path between skills — --next-skill at end-of-output
  • Keyword sets reviewed at author time for collisions across the shell's skill grant
  • The harness validates skill invocations and tool calls before executing — bounce malformed calls back with the specific validation error, not a generic retry

07.7Implications for the schema

The two-trigger model requires structured fields. skills.content stays as the full workflow body; the trigger surface gets first-class storage so the renderer can project Section F cleanly without parsing prose.

  • Add skills.trigger_explicit TEXT — auto-generated as '--' || name, but stored so the renderer doesn't recompute, and so the operator can override for legacy/short tokens.
  • Add skills.trigger_keywords TEXT — comma-separated list, 3–6 entries. Loose schema (TEXT not JSON) keeps authoring frictionless; the renderer splits on comma at render time.
  • Add skills.trigger_use_when TEXT — single sentence, ≤120 chars. The disambiguator that renders after the keyword list.
  • Keep skills.description — but it becomes a human-readable summary for catalogues and skill management UIs, not the runtime trigger. Out of the prompt's hot path.
  • Keep skills.content — the full workflow, fetched on invocation.

This is the first time we're adding structure to a previously free-form text surface. The cost is real: existing skills need a migration that splits prose descriptions into the three new fields. Worth it for the reliability points and the catalog-level lint ("no two skills share more than one keyword").

The architecture in one line Two triggers. The operator's explicit --name token is the deterministic path; the shell's keyword match plus use when is the inferred path. Both render in Section F. The model never has to choose between them — they're complementary, not alternative.
08

Memory compression

A second AI between turns — chat into context, in parallel.

A small local model (gemma, qwen-coder, or similar) runs alongside the active shell. Every 5–10 messages it reads the recent turns and produces a compact context block. The active shell sees the block as user-role context on its next turn, not as system prompt; the older raw messages drop out of the window.

08.1What the summarizer produces

  • A 2–3 sentence summary of where the work stands
  • Candidate decisions worth capturing in shell_decisions
  • Candidate seed / L&S moments — surfaced, never auto-committed (Law 3 spirit)
  • Flag movement — opened, resolved, blocked

08.2Where outputs land

  • Summary → injected as user-role message on the next turn, replacing the now-compressed older turns
  • Decisions → POST /shells/{id}/decisions automatically only if confidence is high; else surfaced to the active shell as a candidate to confirm
  • Identity candidates → never auto-committed; surfaced as a prompt to the active shell
  • Flag movement → suggested writes only; active shell confirms before committing

08.3Effect on the renderer

The system prompt + harness re-renders every round either way — that cost is already paid. What changes:

active shell context per turn =
    system prompt (rendered, ~6–7k)
  + compressed summary of older turns
  + last K raw turns         (K ≈ 5, never compressed)
  + current user input
Coherence risk What if the active shell makes a decision the summarizer just compressed away? Mitigation: always keep the last K turns raw; only compress turns older than K. Decisions land in the API record, not just chat, so they survive the compression anyway.

08.4Storage

Two options. Either write summaries as [HH:MM] (auto) {…} lines to shell_memory_archives.full_narrative (no schema change; mixes auto with manual), or add a dedicated compression_summaries table (queryable, separable). Open question #4.

09b

Token accounting

Stop estimating. Measure.

The token numbers throughout this spec were estimated using a 4-chars-per-token heuristic. Real tokenization, measured against the dev shell rendered prompt, came in roughly half of those estimates. The spec's numbers were honest planning figures; they were also wrong by a factor of two. This section fixes the spec by replacing the heuristic with a real counter, and fixes the runtime by hooking that counter into the substrate so the chat_messages.tokens column finally has data in it.

Discovery Dev shell rendered prompt, measured: 9,190 chars, 2,244 tokens. Spec said: ~18,540 chars, ~4,635 tokens. The character estimate was ~2x too high; the chars-per-token ratio was actually ~4.1, not the conservative ~4.0 used in the spec. Both errors compounded in the same direction.

09b.1The counter

tiktoken, OpenAI's BPE tokenizer, is the pragmatic default. It's installed on Arch as python-tiktoken (or pip tiktoken). It's fast, has no GPU dependency, and gives counts within ~15% of any major model's native tokenizer — well inside the tolerance for planning, monitoring, and budget warnings. cl100k_base is the encoding to use.

Particularly useful: most local models that support tooling (Qwen3, Llama 3.1+, Hermes Pro) tokenize close to OpenAI's encoding by design — they target the OpenAI tools API as their reference dialect, and their tokenizers are tuned for similar BPE behavior. tiktoken's count for these models is typically within 5–10%, not 15%. Anthropic's tokenizer is also BPE-based and lands in the same window. The parsed-dialect path (raw Llama/Qwen output) sees ~10% overhead, still inside tolerance.

# shell_core/utils/tokens.py
import tiktoken

_ENC = tiktoken.get_encoding("cl100k_base")

def count_tokens(text: str) -> int:
    """Token count using cl100k_base. Within ~15% of any model's native
    tokenizer; closer for tool-trained OpenAI-API-compatible models."""
    if not text:
        return 0
    return len(_ENC.encode(text))

One function. No dialect parameter, no multiplier table. The simplicity is the point — token counts are a monitoring surface, not a billing surface, and the ±15% envelope is what we have to live with regardless of how clever the counter is.

09b.2Audit what's already being counted

The schema already has fields suggesting token tracking happens somewhere: chat_messages.tokens, chat_sessions.total_tokens, chat_sessions.token_warning_sent, users.chat_history_window. Some of these have populated values. Before adding the new counter, audit what's currently writing to these — otherwise we either double-count (new counter writes alongside old) or contradict (new counter reports 2,244, old reports something else, the warning logic fires on whichever it reads last).

Audit steps, in order:

  1. Find where chat_messages.tokens is written. git grep -n "tokens" shell_core/ | grep -i "INSERT\|UPDATE\|tokens=" — locate every write site. There may be one, none, or several from earlier experiments.
  2. Sample existing values against tiktoken ground truth. Pull a handful of recent chat_messages rows, run their bodies through count_tokens, compare stored value vs measured. Likely outcomes: stored values are wildly off (heuristic-based), stored values are NULL (column unused), or stored values match tiktoken (someone already did the right thing). The third is unlikely but worth checking.
  3. Decide: replace, augment, or co-exist. Most likely: the existing logic is heuristic-based (chars/4, word count × 1.3, or similar) and should be replaced wholesale. If it co-exists with the new counter, the new path wins; remove the old.
  4. Backfill or leave. If chat_messages.tokens has historical NULL or wrong values, decide whether to backfill. Cheap: UPDATE chat_messages SET tokens = ? WHERE message_id = ? in a one-time script reading each body through tiktoken. Skip if the historical numbers don't matter for any active workflow.
Suspected current state Best guess based on the schema shape: chat_messages.tokens is populated by something approximate (likely chars/4 or word-based), and chat_sessions.total_tokens rolls up those approximate values. token_warning_sent likely fires on a threshold against that roll-up. If true, the warning has been firing on inflated counts (so it fires too early, which is the harmless failure mode — better than firing too late and overflowing).

09b.4Renderer integration

The renderer already assembles the prompt; counting is a one-line addition at the end:

# shell_core/scripts/run.py (excerpt)
from shell_core.utils.tokens import count_tokens

def render_shell_prompt(shell_id: int) -> str:
    # ... existing assembly steps ...
    rendered = "\n\n".join(sections)

    # NEW: count and log
    tok = count_tokens(rendered)
    chars = len(rendered)
    logger.info(f"shell={shell_id} render: {chars} chars, {tok} tok")

    return rendered

This gives observability without storage. Every render leaves a measurable trace in the log; trends over time are visible by grep, and outliers (a shell whose prompt suddenly jumped 30%) become visible without instrumentation.

09b.5API message handler integration

The chat_messages.tokens column has been in the schema unused. Populate it on insert:

# shell_core/api/chat.py (excerpt)
from shell_core.utils.tokens import count_tokens

@router.post("/shells/{shell_id}/messages")
def post_message(shell_id: int, payload: MessageIn, db = Depends(get_db)):
    tok = count_tokens(payload.body)

    msg = ChatMessage(
        shell_id=shell_id,
        direction=payload.direction,
        body=payload.body,
        tokens=tok,
        chat_session_id=payload.chat_session_id,
    )
    db.add(msg)

    # roll up session total
    db.execute(
        "UPDATE chat_sessions SET total_tokens = total_tokens + :t, "
        "last_active = CURRENT_TIMESTAMP WHERE chat_session_id = :sid",
        {"t": tok, "sid": payload.chat_session_id}
    )
    db.commit()
    return msg

From this point on, SELECT total_tokens FROM chat_sessions WHERE shell_id = ? returns real numbers. The compression trigger (Tab 08) reads from this. The "this session is approaching the model's context window" warning that chat_sessions.token_warning_sent is meant to gate now has a value to compare against.

09b.7What changes in the spec

The token estimates throughout this spec — particularly in Tab 11 — are now measured for the dev shell and projected for the others using the real 4.1 chars/token ratio. The methodology note in Tab 11 acknowledges the previous numbers were estimates and have been corrected. Mature shell projections come down accordingly, putting the system more comfortably inside the 6–7k aim than the inflated estimates suggested.

09b.8Caveats

  • tiktoken isn't Llama, Qwen, or Claude's tokenizer. Counts are within ~15% but not exact. For precise budgeting against a specific model's context window (rare — most decisions are made well inside the 15% margin), use that model's tokenizer directly: transformers.AutoTokenizer for Llama/Qwen, Anthropic's SDK helper for Claude.
  • Counts age slowly. Tokenizer vocabularies are stable but not immutable. If a model updates its tokenizer in a breaking way (Claude's claude-3-5-sonnet → claude-4 family didn't, but it could happen), the dialect multipliers need revisiting.
  • cl100k_base ages too. OpenAI's newer models use o200k_base. If you want tighter alignment with current GPT models specifically, swap the encoding. For all other models, cl100k_base is fine — both encodings agree to within a few percent on typical content.
  • Don't store token counts on identity entries. Bodies change tokenization with model updates; storing a static count creates drift. Recompute at render time.
Why this section earns its weight Token budgets are how we know whether the architecture fits. Estimates that are 2x wrong don't tell us that. tiktoken is one import, one function, two integration points — cheap to install, hard to regret, hooks directly into the schema columns already designed for it.

Open questions

Settle these before the renderer goes live.

  1. Re-render frequencyPer session only, or per-turn for current_state propagation? Per-turn costs latency; per-session may show a stale rolling status until next boot.
  2. Recent decisions render policyTop N by date? Since last close? Never (lazy-load only)? Affects section K.
  3. Compression cadenceFixed per-shell (e.g., shells.compression_window field), system-wide constant, or adaptive (token-pressure-driven)?
  4. Summarizer output locationWrite into shell_memory_archives.full_narrative as tagged lines, or add a dedicated compression_summaries table?
  5. Universal / per-shell seamSingle Jinja-style template with slot-fills, or two-file concat (universal.md + shell-specific.md)? Affects ergonomics of editing the universal layer.
  6. Parsed-example backfillWhen does tools.parsed_example get populated across the catalog? First shell on local → that shell's owner authors them?
  7. Lineage seed interaction with pinShould lineage entries default to pin=1? They're already capped at 3 and immutable per Law 6 — pinning seems consistent.
  8. Frontier vs. 8B rendering divergenceSame renderer, different gates? Or two distinct templates? My lean: same renderer, dialect/model_class gates per section. Simpler.
  9. Skill authoring conventionsThe trigger surface is now structured (explicit / keywords / use-when). The skills.content workflow body remains free-form. Sub-spec for content structure (purpose · tools · workflow · never · stop), or convention-by-example through a few well-authored seed skills? Probably the latter first, the former when patterns settle.
  10. Keyword backfill responsibilityThe migration adds trigger_keywords and trigger_use_when as nullable. Existing skills need them populated. Done lazily as each skill is next edited, or as a one-time pass through skill_management at migration time?
  11. The skill-escape hatchA meta-skill no_skill_needed the model can invoke when nothing fits, or a section-F rule that says "if none of these triggers fire, respond directly without invoking a skill"? Both work; the meta-skill is more explicit, the rule is cheaper in tokens.

Methodology notes

The token figures above were originally estimated using a 4-chars-per-token rule of thumb. Measured against tiktoken's cl100k_base encoding, the dev shell rendered prompt is 9,190 chars / 2,244 tokens — roughly half the originally-estimated 18,540 / 4,635. The character counts in the tables were inflated; the actual chars-per-token ratio is ~4.1, not the conservative ~4.0 used in early planning.

The numbers shown have been adjusted downward where possible, but the per-section character estimates in the token tables remain planning figures — the only measured number is the dev shell total. For the planning and assistant shells, the totals are derived by applying the same 4.1 ratio to revised character estimates. Treat all per-section counts as approximations. Treat the dev shell total as measured. Treat the others as projections.

Going forward, the token-accounting integration in Tab 09b replaces estimation entirely — every render and every chat message gets a real tiktoken count, stored on chat_messages.tokens and rolled up to chat_sessions.total_tokens. The spec stops needing these estimates once the renderer ships.
